# OWASP Juice Shop Login Form Assignment

This assignment explores web security through a secure feature design, a working login form, and documented injection attempts. The standalone form uses HTML, CSS, JavaScript, and a Node.js server. It is inspired by Juice Shop's login page and has its own demo account; it does not connect to Juice Shop's database.

## Run the form

Install Node.js **22.16.0 or newer**, as required by the project. From the repository root:

```sh
cd login-form
npm ci
npm start
```

Open **http://localhost:3001** in your browser. Keep the terminal running while using the form, and stop the server with **Ctrl+C**.

| Demo field | Value |
| --- | --- |
| Email | `student@example.com` |
| Password | `Student123!` |

The demo credentials are intentionally public. Use sample data only. Accounts are held in an in-memory SQLite database, and restarting the server discards sessions. A Node.js experimental SQLite warning may appear; it does not prevent the form from running. Juice Shop, if running separately, uses port 3000.

## Implementation

- Email and password fields include labels, a password visibility toggle, and accessible feedback.
- The shared JavaScript `validateLogin()` function rejects empty fields, emails without `@`, and passwords shorter than eight characters. It also limits email length to 254 characters and passwords to 72 UTF-8 bytes for bcrypt compatibility.
- The browser validates before submitting. The server independently validates every login request, so the rules still apply when browser validation is bypassed.
- SQLite prepared statements bind submitted email as data, preventing it from changing query syntax.
- Passwords are stored as salted bcrypt hashes using `bcrypt.hash(password, 12)` and checked with `bcrypt.compare()`.
- Submitted email is displayed with `textContent`, so it is rendered as text rather than HTML. A Content Security Policy adds another layer of protection.
- Successful authentication creates a random, server-side session that expires after 15 minutes. Its cookie uses `HttpOnly` and `SameSite=Strict`.
- Invalid credentials receive a generic response. Unexpected request fields are rejected, roles come from the database, and login attempts are rate-limited.

These are defenses for a local classroom demonstration. Production deployment would require HTTPS, Secure cookies, durable account/session storage, and additional account-management controls.

## Verify normal behavior

1. Click **Log in** with both fields empty: the form displays field errors.
2. Enter an email without `@` or a password shorter than eight characters: submission is blocked by browser validation.
3. Enter the demo credentials: the form displays **Login successful.**
4. Submit a validly formatted but incorrect password: the form displays **Invalid email or password.**

From the `login-form` directory, the project's checks are:

```sh
npm test
npm run lint
npm run check
```

The test files cover validation, authentication, rejection of injection inputs, session behavior, rate limiting, safe feedback, and browser interaction. Browser behavior tests use jsdom; they do not replace verification in a real browser. Failed attack attempts demonstrate protection against the tested inputs, not the absence of every possible vulnerability.

`OWASP Juice Shop - Zaahir Sharma.pdf` is the single submission document. It contains:

1. **Secure feature design:** observed Juice Shop SQL injection, search XSS, and client-supplied registration roles, with proposed mitigations and a bcrypt example.
2. **Form implementation:** the HTML/JavaScript login form, browser and server validation, and implementation screenshots.
3. **Exploitation attempts:** rejected SQL injection and XSS inputs on the standalone form, observed outcomes, and a suggested rendering fix.
